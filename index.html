Q1. What is a Database System? Explain its Purpose and Importance in Modern Organizations.
1. Definition of Database System

A database is an organized collection of related data stored electronically.

A Database Management System (DBMS) is software used to create, store, retrieve, update, and manage data in a database.

Database System = Database + DBMS + Application Programs + Users
2. Diagram of Database System

Users use application programs. The application communicates with the DBMS, and the DBMS manages the data stored in the database.

3. Purpose of a Database System
  1. Store data – Keeps large amounts of data in an organized way.
  2. Retrieve data easily – Allows users to quickly search for required information.
  3. Update data – Makes adding, modifying, and deleting data easy.
  4. Reduce redundancy – Avoids unnecessary duplication of data.
  5. Maintain consistency – Keeps data accurate and consistent.
  6. Provide security – Controls who can access or modify data.
  7. Handle multiple users – Allows many users to access data safely at the same time.
  8. Maintain data integrity – Enforces rules and constraints on stored data.
4. Importance in Modern Organizations

Database systems are important because organizations deal with large amounts of data every day.

They help organizations to:

  • make data available quickly,
  • manage data efficiently,
  • protect important information,
  • reduce errors and duplication,
  • support multiple users,
  • and maintain reliable and consistent data.

Example

In a college database system, information about students, courses, faculty, and marks can be stored in the database. The college portal can use the DBMS to add a new student, update marks, or search for students who scored above 90%.

Q2. Design an ER Diagram for a Library Management System, identifying entities, attributes, keys, and relationships.

An ER (Entity-Relationship) Diagram is a graphical representation of the structure of a database. It shows entities, their attributes, keys, and relationships between entities.

ER Diagram of Library Management System:

1. Entity

An entity is a real-world object about which data is stored in a database.

In the Library Management System, the main entities are:

  • BOOK – represents books in the library.
  • MEMBER – represents people who borrow books.
  • PUBLISHER – represents publishers of books.

In an ER diagram, an entity is represented by a rectangle.

2. Attributes

An attribute is a property or characteristic that describes an entity.

  • BOOK: Book_ID, Title, Author, Price
  • MEMBER: Member_ID, Name, Phone, Address
  • PUBLISHER: Pub_ID, Name, Address

In an ER diagram, an attribute is represented by an oval.

3. Keys

A key is an attribute that uniquely identifies each entity record.

  • Book_ID → Primary Key of BOOK
  • Member_ID → Primary Key of MEMBER
  • Pub_ID → Primary Key of PUBLISHER

In an ER diagram, key is shown by underlining the attribute name.

4. Relationships

A relationship shows how two or more entities are connected.

BORROWS

  • Connects MEMBER and BOOK.
  • A member can borrow many books, and a book can be borrowed by many members over time.
  • Cardinality: Many-to-Many (M:N)
  • Relationship attributes: Issue_Date, Return_Date

PUBLISHED_BY

  • Connects BOOK and PUBLISHER.
  • One publisher can publish many books, while each book is published by one publisher.
  • Cardinality: Many-to-One (N:1)

In an ER diagram, a relationship is represented by a diamond.

Q3. Assess the Concept of Relational Databases and Their Key Characteristics.

A Relational Database stores data in the form of tables. Each table contains rows and columns. The relational model was introduced by E. F. Codd in 1970.

Example of Relational Database
Key Characteristics
  1. Table-based Structure
    Data is organized in tables containing rows and columns.
    Example: STUDENT TABLE.
  2. Relation
    A table is called a relation.
    Example: STUDENT TABLE is a relation.
  3. Tuple
    A row is called a tuple or record.
    Example: 101 | Rahul | B.Sc. CS | 8.2 is one tuple.
  4. Attribute
    A column is called an attribute or field.
    Example: ID, Name, Program, CGPA are attributes.
  5. Domain
    A domain specifies the allowed values or data type of an attribute.
    Example: CGPA contains numeric values.
  6. Keys
    Keys identify records and help establish relationships between tables.
    Primary Key: uniquely identifies a record. ID can be the primary key in this table.
    Foreign Key: refers to the primary key of another table.
  7. Degree
    The number of columns in a relation is called its degree.
    Here, Degree = 4 (ID, Name, Program, CGPA).
  8. Cardinality
    The number of rows in a relation is called its cardinality.
    Here, Cardinality = 3 because there are 3 student records.
Conclusion

A relational database organizes data into relations (tables) using attributes, tuples, domains, and keys. Degree and cardinality describe the structure of a relation.

Q4. Explain the Concept of Transaction Management in a Database System.
1. Meaning of Transaction Management

Transaction Management is the process of managing database transactions so that they are completed correctly, safely, and reliably.

A transaction is a single logical unit of work in a database. It follows an all-or-nothing approach.

Example:

In a bank transfer of ₹5,000:

  • ₹5,000 is debited from Account A.
  • ₹5,000 is credited to Account B.

Both operations must be completed. If an error occurs, the transaction should be cancelled to avoid incorrect data.

2. Diagram of Transaction States

States shown in the diagram:

  • Active: Transaction is being executed.
  • Committed: Transaction completed successfully and changes become permanent.
  • Failed: An error occurs during the transaction.
  • Aborted: Failed transaction is cancelled and its changes are undone.
3. ACID Properties

A – Atomicity:
All operations of a transaction are completed, or none are completed.

C – Consistency:
The database remains in a valid state before and after the transaction.

I – Isolation:
Multiple transactions can run at the same time without interfering with each other.

D – Durability:
Once a transaction is committed, its changes remain permanent even after a system failure.

ACID properties help maintain the integrity and consistency of the database.

Q5. Discuss the Concept of "View of Data" in a Database System with the Help of Three-Level Architecture.

View of Data means showing database information at different levels of abstraction. It hides unnecessary details and allows users to see only the data they need.

Three levels of Data Abstraction (ANSI/SPARC):

1. Levels of Data Abstraction

1. External Level (View Level)

  • Highest level of abstraction.
  • Shows only the data required by a particular user or application.
  • Different users can have different views.
  • Example: A student sees marks, while an administrator sees student and fee details.

2. Conceptual Level (Logical Level)

  • Describes the complete logical structure of the database.
  • Shows what data is stored and the relationships between data.
  • It does not describe how data is physically stored.

3. Internal Level (Physical Level)

  • Lowest level of abstraction.
  • Describes how data is actually stored in the computer.
  • Includes files, indexes, pointers, and storage structures.
2. Schema and Instance
  • Schema: Overall logical design or structure of the database. It changes rarely.
  • Instance: Actual data stored in the database at a particular moment. It changes frequently.
3. Importance of Three-Level Architecture
  • Hides unnecessary database details.
  • Provides different views for different users.
  • Makes database management easier.
  • Provides data independence.
  • Changes at one level can be made with less effect on other levels.
Q7. Describe the Database Architecture (Client-Server, Centralized, Distributed) with a Suitable Diagram.

Database Architecture describes how the database, DBMS, users, and applications are organized and connected.

The three common architectures are Centralized, Client-Server, and Distributed Database Architecture.

1. Centralized Database Architecture

In a centralized database, the database and DBMS are located at one central server/system. Users access the same central database.

Example: A college keeps all student records in one central database.

Main feature: Data is stored and managed at one central location.

2. Client-Server Architecture

In client-server architecture, the client sends requests to a database server. The server processes the requests and returns the required data.

Example: A college marks portal where students use a web application to request their marks from the database server.

Main feature: The client handles user interaction, while the server manages the database.

3. Distributed Database Architecture

In a distributed database, data is stored at multiple network-connected locations. The locations work together as one database system.

Example: A bank maintains databases at different branches that are connected through a network.

Main feature: Data is distributed across multiple locations but can be accessed as part of one database system.

4. Comparison
Architecture Data Location Main Idea
Centralized One location Single central database
Client-Server Server Clients request data from server
Distributed Multiple locations Data distributed across network
Q8. What are Data Models? Discuss the Evolution of Data Models from Hierarchical to Relational and Object-Oriented Models.

A data model is a collection of concepts and notations used to describe:

  • Data
  • Relationships between data
  • Constraints on data

It provides a common language for database designers, developers, and users to understand how data is organized.

2. Evolution of Data Models

Data models evolved over time to handle increasingly complex data and requirements.

3. Major Data Models
  1. File-Based Model
    • Used in the early 1960s.
    • Data was stored in separate files.
    • Managing relationships between files was difficult.
  2. Hierarchical Model
    • Developed during the 1960s–1970s.
    • Organizes data in a tree-like structure.
    • Supports parent-child relationships.
    • One parent can have many children.
  3. Network Model
    • Developed during the 1960s–1970s.
    • Represents data using a network of relationships.
    • Supports more complex relationships than the hierarchical model.
  4. Relational Model
    • Introduced by E. F. Codd in 1970.
    • Organizes data into tables consisting of rows and columns.
    • Uses keys and relationships to connect tables.
    • Became the dominant traditional database model.
  5. Object-Oriented Model
    • Became important during the 1980s–1990s.
    • Represents data as objects, combining data and behavior.
    • Useful for complex data and object-oriented applications.
